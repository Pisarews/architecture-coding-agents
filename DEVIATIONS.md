# Deviations from the preregistration

Every change made after the preregistration was frozen (`prereg-v1`) goes here, with its date and reason.
The paper reports all entries.

| Date | Section | Change | Reason | Affects confirmatory test? |
|---|---|---|---|---|
| 2026-10-13 | §2.4 Randomization (execution) | Execution runs in parallel workers, one per run (2 at a time from 11:30, 3 at a time from 11:50; `harness/run_phase1.py`, env `PHASE1_PARALLEL`). Each worker interleaves the six architecture × model trajectories of its run, task position by task position, in seeded random order (seed 20261012 + 1000 × run). This replaces a single queue over all 30 trajectories. | Wall-clock time: a single sequential queue would take about 70 h. | No. Every worker still contains all arms, so drift is spread over all arms as intended. Outcomes are unaffected. |
| 2026-10-13 | §6.1 secondary models, §6.5, H6 | `analysis/analyze.py` was completed with analyses that the registration specifies but the frozen script lacked: the GLMM/LMMs (statsmodels; the logistic GLMM uses variational Bayes, `BinomialBayesMixedGLM`), the `dependency_failed` sensitivity analysis, and the one-sample "slope > 0" test for H6. `analysis/power_sim.py` now defaults to the registered 24-task design. | Gaps found while drafting the paper. The change was made **before any Phase 1 outcome was inspected**; data collection was running and the analysis had not been run on Phase 1 data. | No. It implements already-registered analyses; the primary tests are unchanged. |
| 2026-10-14 | Execution | All collection processes stopped at about 09:25 (host session ended), with R1–R3 complete and R4 at 30/144. The cost rule had already run at 07:20 (forecast $30.24 > $30), so R5 was dropped as preregistered. R4 resumed at 14:50 in two parallel workers, one per model; each worker still interleaves all three architectures. The interrupted attempt was rolled back and rerun. The orchestrator now treats the cost-rule decision as final across restarts. | Host interruption; wall-clock time. | No. |
| 2026-10-14 | §4.3 measurement | `harness/erosion.py` now takes each task's snapshot from the commit that was graded (`results.jsonl`) rather than from first-parent git history. In one trajectory (layered/weak/R4) the agent ran `git reset --hard` during T21, which removed the T20 commit from history. The graded T20 commit object still existed and was measured. | Measurement must use the same snapshot that was graded. | No. It fixes one missing measurement (599 → 600 commits); all other snapshots are identical. |
| 2026-10-15 | §3.3 Tasks (validation) | Post-hoc **reference solutions** for all 24 tasks in all three variants, built cumulatively and graded with the experiment's grader (`harness/grade_one.py`, `data/reference/`). Also a **quality review** of a stratified sample of successful agent attempts (`data/review/`). | The preregistration planned reference solutions, but before registration only FAIL_TO_PASS validation and a partial reference (12 tasks, NONE) had been done. T18 and T23 were never solved by any agent. | Primary analyses unchanged. If a hidden test turns out to be faulty, a sensitivity analysis excluding that task is reported as **exploratory**. |
| 2026-10-15 | §4.2 Success (grading reliability) | While building reference solutions, the grader produced false failures under heavy Docker load (many unrelated tests failing; a re-run of the same commit was clean). All 403 attempts recorded as failures are therefore **re-graded at low load** with the same grader (`harness/regrade.py`, `data/phase1/regrade.jsonl`). An attempt whose outcome differs is graded a third time, and the majority decides. All 10 recorded "application did not start" cases were checked and show real exceptions in agent code. | Phase 1 ran three workers in parallel, so the same load-related false failures may have occurred. | Primary results stay as recorded. A sensitivity analysis with re-graded outcomes is reported. A false failure can only lower success, and execution was interleaved across arms, so any bias between architectures is expected to be small. |
| 2026-10-15 | Outcome of the post-hoc checks | (a) Reference solutions: 24/24 tasks pass cumulatively in all three variants with 0 regressions, so no hidden test is faulty. (b) Re-grade: all 403 recorded failures were re-graded at low load; **0 outcomes changed**, and built/started/task-tests-passed matched in every case. Phase 1 grading was not affected by the flakiness. (c) Full baseline validation of all 24 tasks: 72/72 OK, after re-running two checks that had been OOM-killed while three builders ran in parallel. (d) Quality review: 26/27 sampled strong-model successes are genuine implementations, none games the tests. | Post-hoc validity checks. | No. The confirmatory results stand; no sensitivity analysis is needed for grading. |
